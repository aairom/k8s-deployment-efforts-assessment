1 Executive Summary

IBM Cloud offers two premier managed container platforms designed to meet the divergent needs of modern enterprise workloads. Both services are underpinned by IBM's proven global cloud infrastructure, benefit from a fully managed control plane, and integrate natively with the broader IBM Cloud service ecosystem. Despite sharing foundational infrastructure, they represent philosophically distinct approaches to container orchestration at enterprise scale.

IBM Cloud Kubernetes Service (IKS) IKS

  • CNCF-certified, upstream-aligned Kubernetes
  • Fully managed control plane — no master node ops
  • Ubuntu 20.04/22.04 LTS or RHEL 8 worker OS
  • containerd container runtime
  • Pure resource consumption pricing (no platform license)
  • Maximum cross-cloud portability
  • Latest Kubernetes minor releases available

Core Value Proposition: Maximum Kubernetes conformance, lowest TCO for pure container workloads, and broadest compatibility with the CNCF ecosystem toolchain.

Red Hat OpenShift on IBM Cloud (ROKS) ROKS

  • Red Hat OpenShift Container Platform (OCP) 4.x
  • Fully managed control plane with dedicated masters
  • RHCOS (immutable) or RHEL 8 worker OS
  • CRI-O container runtime; SELinux enforcing
  • Bundled OCP license in worker node pricing (~25–30% premium)
  • IBM Cloud Paks exclusive deployment target
  • Integrated developer platform: Console, S2I, Pipelines, OLM

Core Value Proposition: Enterprise security defaults, integrated developer platform, seamless IBM Cloud Pak deployment, and consistent hybrid cloud operations.

2 Architectural Deep-Dive & Control Plane Mechanics

2.1 Control Plane Management

Both IKS and ROKS operate under a fully managed control plane model. IBM provisions, operates, monitors, and patches the Kubernetes/OpenShift master components (API server, etcd, controller manager, scheduler) on behalf of the customer, eliminating the single largest operational burden in self-managed Kubernetes deployments.

2.2 Worker Node Operating Systems

IKS — Worker Node OS
  • Ubuntu 20.04/22.04 LTS or RHEL 8 (flavor-dependent)
  • CIS Benchmark-aligned OS configuration enforced by IBM SREs
  • Node patching via full re-imaging: ibmcloud ks worker update
  • containerd as the container runtime (OCI-compliant)
  • LUKS AES-256 encryption on container filesystem partition (default)
  • SSH access disabled; unique LUKS key per worker node
  • Linux kernel supports containers from any Linux distribution
ROKS — Worker Node OS
  • Red Hat Enterprise Linux CoreOS (RHCOS) — immutable, container-optimized OS
  • Managed declaratively via Ignition; rpm-ostree for atomic image-based updates
  • Read-only system partitions; OS state is ephemeral and version-controlled
  • CRI-O container runtime (mandated by OpenShift)
  • SELinux enforcing mode — mandatory access control at OS layer
  • MachineConfigOperator (MCO) manages OS configuration as code
  • RHEL 8 also available for certain worker pool configurations
⚠ RHCOS Implication The immutable nature of RHCOS means no ad-hoc OS modifications; all configuration is declarative via MachineConfig objects. This enforces consistency at scale but requires teams to adjust operational practices away from traditional mutable server management.

2.3 Internal System Components

IKS — System Components
  • Ingress: IBM NGINX-based Application Load Balancer (ALB); one ALB per zone in MZC
  • Registry: No built-in registry; IBM Cloud Container Registry (ICR) via pull secrets
  • Auth: IBM Cloud IAM → Kubernetes RBAC ClusterRole binding sync
  • CNI: Project Calico for pod networking and NetworkPolicy enforcement
  • Konnectivity: IBM TLS tunnel agent for master ↔ worker secure comms
  • Admission: Standard Kubernetes admission chain (PodSecurity, RBAC, webhooks)
  • Operators: No built-in framework; manual install via kubectl/Helm
ROKS — System Components
  • Router: HAProxy-based OpenShift Router (Operator-managed); one per zone; handles Route resources
  • Internal Registry: Built-in OCP registry backed by mandatory IBM COS; supports ImageStreams
  • OAuth Server: Auto-configured to delegate to IBM Cloud IAM; custom IdP not configurable
  • CNI: Project Calico (same as IKS)
  • Konnectivity: Same IBM TLS tunnel agent
  • Admission: Extended chain: SCC, BuildByStrategy, OriginPodNodeEnvironment, OCP-specific webhooks
  • OLM + OperatorHub: Pre-installed operator lifecycle management framework
  • Web Console: Pre-deployed; Developer + Admin perspectives

3.2 Single-Zone vs. Multi-Zone Cluster Topologies

Single-Zone Cluster (SZC)
  • All worker nodes and master replicas in a single AZ
  • Master still has 3 replicas for process-level HA within the zone
  • AZ failure causes full cluster unavailability
  • Suitable for dev, test, CI, and non-critical workloads
  • Lower cost; single zone networking and billing
Multi-Zone Cluster (MZC) — Production Standard
  • Worker nodes distributed across 2–3 AZs in an MZR
  • Master replicas: one per zone (3 total)
  • IKS: NGINX ALBs one per zone; MZC LB auto-provisioned
  • ROKS: Router services one per zone; VPC LBs front routers
  • Internal registry COS bucket: regional resource, 11-nines durability
  • IKS: ≥1 node/zone; ROKS: ≥2 nodes/zone (4 vCPUs each)

3.3 Hybrid and Multi-Cloud: IBM Cloud Satellite

Both IKS and ROKS extend to customer-managed infrastructure via IBM Cloud Satellite, enabling IBM-managed control planes on hardware in customer data centers, co-location facilities, edge locations, or third-party clouds (AWS, Azure, GCP).

4.3 Network Isolation Primitives

Shared Network Architecture Both IKS and ROKS use Project Calico as the CNI plugin. Kubernetes NetworkPolicy objects provide L3/L4 micro-segmentation. Both platforms support private-only cloud service endpoints routing API server communication over the IBM Cloud private backbone. VPC clusters additionally enforce security groups at the NIC, load balancer, and VPE gateway layers for defense-in-depth isolation.

5 Key Distinctions & Operational Differences

5.1 Developer & Operator Experience

IKS — Kubernetes-Native Toolchain
  • CLI: kubectl + ibmcloud ks plugin for cluster lifecycle
  • UI: IBM Cloud Console (infra mgmt); K8s Dashboard deployable manually
  • Package Management: Helm 3 — de facto standard for complex app deployments
  • Operators: Manual install via kubectl apply or Helm; no built-in framework
  • CI/CD: IBM Cloud Continuous Delivery, GitHub Actions, Jenkins, ArgoCD, Flux
  • Registry: IBM Cloud Container Registry; pull secrets managed manually
  • Self-service: No built-in developer portal; relies on external tooling
ROKS — Integrated Developer Platform
  • CLI: oc (kubectl superset) + kubectl + ibmcloud oc plugin
  • UI: OpenShift Web Console — pre-installed; Developer perspective (topology, S2I, pipelines) + Admin perspective
  • OLM + OperatorHub: Pre-installed; hundreds of certified/community operators
  • CI/CD: OpenShift Pipelines (Tekton) — pre-installed; visual management in Web Console
  • Build System: BuildConfig, S2I, ImageStream triggers — fully built-in
  • Registry: Internal registry (ImageStreams) + ICR; automated promotion workflows
  • Self-service: Developer Perspective: guided app deployment from Git or image without Dockerfile

5.2 Security Posture & Isolation

IKS — Kubernetes Pod Security Standards (PSS)

IKS enforces security via the upstream Kubernetes model. Pod Security Admission (PSA) at the namespace level enforces privileged, baseline, or restricted modes. The restricted profile mandates non-root execution, read-only root filesystems, and Linux capability dropping. Calico NetworkPolicy provides L3/L4 segmentation (not enforced by default — explicit policies required).

ROKS — Security Context Constraints (SCC) — Stricter by Default

ROKS enforces a more opinionated security posture through OpenShift's Security Context Constraints framework, active via the SecurityContextConstraint admission controller in the master admission chain. SCCs control UID/GID ranges, permitted volume types, host network/PID/IPC access, Linux capabilities, and AppArmor/SELinux profiles.

A pre-migration SCC compatibility assessment is strongly recommended. RHCOS enforces SELinux in enforcing mode on all worker nodes — an additional mandatory access control boundary not present on Ubuntu-based IKS workers.

5.3 Build & CI/CD Pipelines

IKS — Composable CI/CD
  • No built-in build or CI/CD system
  • IBM Cloud Continuous Delivery: Managed Tekton Toolchains; Code Risk Analyzer; Secrets Manager integration
  • ArgoCD / Flux: GitOps operators for declarative deployment reconciliation (deployed via Helm)
  • GitHub Actions / GitLab CI / Jenkins: External CI via kubectl + Helm + ICR
  • Tekton Pipelines: Deployable as standalone operator; no pre-installed Console UI
  • Full flexibility to assemble any CNCF-conformant toolchain
ROKS — Integrated Build & Pipeline Platform
  • OpenShift Builds: BuildConfig resources; build pods triggered by Git commits, image changes, or webhooks
  • Source-to-Image (S2I): Push source code → runnable OCI image; no Dockerfile required; enforces security-hardened base images
  • OpenShift Pipelines (Tekton): Pre-installed operator; Pipeline/Task/PipelineRun CRDs; visual management in Web Console
  • ImageStreams: Automated redeploy/rebuild on upstream image CVE patches
  • IBM Cloud Paks: Require OCP; deploy via OperatorHub exclusively on ROKS

5.4 Licensing, Support & Cost Model

IKS — Pure Resource Consumption
  • Worker node cost = infrastructure only (vCPU + RAM + storage)
  • No platform license fee embedded
  • Master management included at no additional charge
  • Classic: 1-year / 3-year reservations → 30–50% savings vs. on-demand
  • Lowest entry cost in IBM Cloud container portfolio
  • VPC regional pricing uplifts + sustained usage discounts apply
ROKS — Compute + Bundled OCP License
  • Worker node cost = infrastructure + OCP license fee
  • New OCP license: 1 license per 2 vCores (or 1 physical core); billed hourly
  • Legacy OCP license: 1 license per 4 vCores; billed monthly per deployed worker
  • OCP license shown as sub-item or separate plan on IBM Cloud invoice
  • BYOL: IBM Cloud Pak entitlement or Red Hat OCP subscription eliminates license surcharge
  • Net effective premium vs. IKS: ~25–30% on equivalent worker flavor
  • Satellite ROKS: flat monthly cluster fee + per-vCPU worker + per-vCPU OCP license

7 Architectural Decision Guide

Use the following scenario-based framework to guide platform selection. Both platforms are production-grade; the decision should be driven by organizational context, existing ecosystem investments, workload security requirements, and total cost of ownership analysis.
Choose IBM Cloud Kubernetes Service (IKS) when…
  1. Scenario 1 — Cost Optimization Budget is the primary constraint and no existing Red Hat license. The ~25–30% OCP license premium is not offset by platform capability requirements. Teams are comfortable assembling their own toolchain (Helm, ArgoCD, Prometheus, external registries).
  2. Scenario 2 — Upstream K8s Conformance Policy mandates latest upstream Kubernetes minor releases. IKS tracks the upstream K8s release cadence more closely than ROKS, which follows the OCP schedule (typically lagging 1–2 minor versions).
  3. Scenario 3 — Multi-Cloud Portability Workloads must be portable to GKE, EKS, or AKS with minimal refactoring. IKS workloads using only upstream K8s APIs are directly portable; ROKS workloads using Route, SCC, BuildConfig, or ImageStream require adaptation.
  4. Scenario 4 — Composable Operator Model Team prefers manual operator ecosystem composition with existing Helm chart investments that may conflict with OLM or require custom SCC grants.
  5. Scenario 5 — Private-Only Classic Cluster Compliance mandates zero public internet exposure including no public worker node networking on Classic infrastructure. IKS supports this; ROKS does not.
  6. Scenario 6 — Minimal Footprint Lightweight edge, CI runner, or dev/test environments. IKS supports 1 worker/zone; ROKS requires ≥2 workers/zone at 4 vCPUs each.
Choose Red Hat OpenShift on IBM Cloud (ROKS) when…
  1. Scenario 1 — Existing OpenShift Ecosystem Organization operates OCP on-premises or on other clouds. ROKS delivers operational consistency: same oc CLI, same SCCs, same OperatorHub, same OCP API surface. Platform engineers' skills and runbooks transfer directly.
  2. Scenario 2 — IBM Cloud Paks Required Any IBM Cloud Pak is part of the solution. Cloud Pak for Data, Integration, AIOps, Business Automation, and Security require OpenShift and deploy only on ROKS (or self-managed OCP).
  3. Scenario 3 — Enterprise Security & Compliance Regulated industry (FSI, Healthcare, Government) requiring FIPS-validated OS, SELinux, and SCC-based pod admission hardening. RHCOS + SCC + OLM provides this posture out of the box.
  4. Scenario 4 — Application Modernization Teams need guided tooling for containerizing legacy applications. S2I, BuildConfig triggers, ImageStream promotion, and the Developer Perspective dramatically reduce time-to-production.
  5. Scenario 5 — Integrated Developer Platform Single platform covering orchestration + registry + CI/CD + catalog + portal + monitoring. ROKS delivers all without additional component installation.
  6. Scenario 6 — Hybrid Standardization via Satellite Multi-environment deployments (IBM Cloud + on-prem + edge). ROKS on Satellite provides a consistent OCP control plane and tooling across all environments from a single IBM Cloud management plane.
  7. Scenario 7 — BYOL License Optimization Existing Red Hat OCP subscription or IBM Cloud Pak entitlement. Applying the entitlement eliminates the OCP license surcharge, making per-node cost comparable to IKS while retaining all OpenShift capabilities.

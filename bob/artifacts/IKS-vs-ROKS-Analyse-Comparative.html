1 Résumé Exécutif

IBM Cloud propose deux plateformes de conteneurs gérées de premier plan, conçues pour répondre aux besoins divergents des charges de travail d'entreprise modernes. Les deux services reposent sur l'infrastructure cloud mondiale éprouvée d'IBM, bénéficient d'un plan de contrôle entièrement géré et s'intègrent nativement à l'écosystème plus large des services IBM Cloud. Malgré leurs fondations infrastructure communes, ces deux plateformes représentent des approches philosophiquement distinctes de l'orchestration de conteneurs à l'échelle de l'entreprise.

IBM Cloud Kubernetes Service (IKS) IKS

  • Kubernetes certifié CNCF, aligné sur l'upstream
  • Plan de contrôle entièrement géré — aucune opération sur les nœuds maîtres
  • OS des nœuds workers : Ubuntu 20.04/22.04 LTS ou RHEL 8
  • Runtime de conteneurs containerd
  • Tarification basée sur la consommation pure (sans licence plateforme)
  • Portabilité maximale entre clouds
  • Dernières versions mineures de Kubernetes disponibles

Proposition de valeur principale : Conformité maximale avec Kubernetes, TCO le plus bas pour les charges de travail conteneurisées pures, et compatibilité optimale avec l'outillage de l'écosystème CNCF.

Red Hat OpenShift on IBM Cloud (ROKS) ROKS

  • Red Hat OpenShift Container Platform (OCP) 4.x
  • Plan de contrôle entièrement géré avec nœuds maîtres dédiés
  • OS workers : RHCOS (immuable) ou RHEL 8
  • Runtime CRI-O ; SELinux en mode enforcing
  • Licence OCP incluse dans le prix des nœuds workers (~25–30 % de surcoût)
  • Cible exclusive de déploiement pour les IBM Cloud Paks
  • Plateforme développeur intégrée : Console, S2I, Pipelines, OLM

Proposition de valeur principale : Sécurité entreprise par défaut, plateforme développeur intégrée, déploiement simplifié des IBM Cloud Paks, et expérience opérationnelle cohérente en environnement hybride.

2 Analyse Architecturale & Mécanique du Plan de Contrôle

2.1 Gestion du Plan de Contrôle

IKS et ROKS fonctionnent tous deux selon un modèle de plan de contrôle entièrement géré. IBM provisionne, exploite, surveille et corrige les composants maîtres Kubernetes/OpenShift (serveur API, etcd, gestionnaire de contrôleurs, planificateur) au nom du client, supprimant ainsi la plus grande charge opérationnelle des déploiements Kubernetes autogérés.

2.2 Systèmes d'Exploitation des Nœuds Workers

IKS — OS des Nœuds Workers
  • Ubuntu 20.04/22.04 LTS ou RHEL 8 selon le type de nœud
  • Configuration OS alignée sur le référentiel CIS Benchmark, gérée par les SRE IBM
  • Correctifs via ré-imagerie complète du nœud : ibmcloud ks worker update
  • Runtime containerd (conforme OCI)
  • Chiffrement LUKS AES-256 sur la partition du système de fichiers conteneur (par défaut)
  • Accès SSH désactivé ; clé LUKS unique par nœud worker
  • Le noyau Linux supporte des conteneurs basés sur n'importe quelle distribution Linux
ROKS — OS des Nœuds Workers
  • Red Hat Enterprise Linux CoreOS (RHCOS) — OS immuable, optimisé pour les conteneurs
  • Géré de manière déclarative via Ignition ; mises à jour atomiques via rpm-ostree
  • Partitions système en lecture seule ; état de l'OS éphémère et versionné
  • Runtime CRI-O (mandaté par OpenShift)
  • SELinux en mode enforcing — contrôle d'accès obligatoire au niveau de l'OS
  • MachineConfigOperator (MCO) gère la configuration de l'OS en tant que code
  • RHEL 8 également disponible pour certaines configurations de pools de workers
⚠ Implication RHCOS La nature immuable de RHCOS interdit toute modification ad hoc de l'OS ; toute configuration est déclarative via des objets MachineConfig. Cela impose la cohérence à grande échelle mais exige des équipes qu'elles adaptent leurs pratiques opérationnelles par rapport à la gestion traditionnelle de serveurs mutables.

2.3 Composants Système Internes

IKS — Composants Système
  • Ingress : Application Load Balancer (ALB) IBM basé sur NGINX ; un ALB par zone en MZC
  • Registre : Aucun registre intégré ; IBM Cloud Container Registry (ICR) via des secrets de tirage
  • Authentification : IBM Cloud IAM → synchronisation des liaisons ClusterRole RBAC Kubernetes
  • Plugin CNI : Project Calico pour la mise en réseau des pods et l'application des NetworkPolicy
  • Konnectivity : Agent de tunnel TLS IBM pour la communication sécurisée maître ↔ worker
  • Admission : Chaîne d'admission Kubernetes standard (PodSecurity, RBAC, webhooks)
  • Opérateurs : Aucun framework intégré ; installation manuelle via kubectl/Helm
ROKS — Composants Système
  • Routeur : OpenShift Router basé sur HAProxy (géré par Operator) ; un par zone ; gère les ressources Route
  • Registre interne : Registre OCP intégré, adossé à IBM COS (obligatoire) ; supporte les ImageStreams
  • Serveur OAuth : Auto-configuré pour déléguer à IBM Cloud IAM ; IdP personnalisé non configurable
  • Plugin CNI : Project Calico (identique à IKS)
  • Konnectivity : Même agent de tunnel TLS IBM
  • Admission : Chaîne étendue : SCC, BuildByStrategy, OriginPodNodeEnvironment, webhooks spécifiques OCP
  • OLM + OperatorHub : Framework de gestion du cycle de vie des opérateurs pré-installé
  • Console Web : Pré-déployée ; perspectives Développeur et Administrateur

3.2 Topologies Mono-Zone vs. Multi-Zone

Cluster Mono-Zone (SZC)
  • Tous les nœuds workers et réplicas maîtres dans une seule zone de disponibilité
  • Le maître maintient 3 réplicas pour une HA au niveau processus dans la zone
  • Une défaillance de zone entraîne l'indisponibilité complète du cluster
  • Adapté aux environnements de développement, test, CI et aux charges non critiques
  • Coût réduit ; réseau et facturation mono-zone
Cluster Multi-Zone (MZC) — Standard de Production
  • Nœuds workers répartis sur 2–3 zones de disponibilité dans une MZR
  • Réplicas maîtres : un par zone (3 au total)
  • IKS : ALBs NGINX un par zone ; LB MZC auto-provisionné
  • ROKS : Services routeur un par zone ; VPC LBs devant les routeurs
  • Registre interne (bucket COS) : ressource régionale, durabilité 11 neuf
  • IKS : ≥1 nœud/zone ; ROKS : ≥2 nœuds/zone (4 vCPU chacun minimum)

3.3 Hybride et Multi-Cloud : IBM Cloud Satellite

IKS et ROKS s'étendent tous deux à l'infrastructure gérée par le client via IBM Cloud Satellite, permettant des plans de contrôle gérés par IBM sur du matériel situé dans les centres de données clients, des installations de co-location, des emplacements de périphérie, ou des clouds tiers (AWS, Azure, GCP).

4.3 Primitives d'Isolation Réseau

Architecture Réseau Commune IKS et ROKS utilisent tous deux Project Calico comme plugin CNI. Les objets Kubernetes NetworkPolicy assurent la micro-segmentation L3/L4. Les deux plateformes supportent les points de terminaison de service privés exclusifs, acheminant toutes les communications du serveur API via le réseau privé IBM Cloud. Les clusters VPC appliquent en outre des groupes de sécurité au niveau de la NIC, de l'équilibreur de charge et de la passerelle VPE pour une isolation en profondeur.

5 Distinctions Clés & Différences Opérationnelles

5.1 Expérience Développeur & Opérateur

IKS — Outillage Natif Kubernetes
  • CLI : kubectl (standard upstream) + plugin ibmcloud ks pour le cycle de vie des clusters
  • Interface : IBM Cloud Console (gestion infra) ; Kubernetes Dashboard déployable manuellement
  • Gestion de paquets : Helm 3 — standard de fait pour les déploiements d'applications complexes
  • Opérateurs : Installation manuelle via kubectl apply ou Helm ; aucun framework intégré
  • CI/CD : IBM Cloud Continuous Delivery, GitHub Actions, Jenkins, ArgoCD, Flux
  • Registre : IBM Cloud Container Registry ; secrets de tirage gérés manuellement
  • Libre-service : Aucun portail développeur intégré ; dépend d'outils externes
ROKS — Plateforme Développeur Intégrée
  • CLI : oc (sur-ensemble de kubectl) + kubectl + plugin ibmcloud oc
  • Interface : Console Web OpenShift pré-installée ; perspective Développeur (topologie, S2I, pipelines) + perspective Administrateur
  • OLM + OperatorHub : Pré-installés ; des centaines d'opérateurs certifiés et communautaires
  • CI/CD : OpenShift Pipelines (Tekton) pré-installé ; gestion visuelle des pipelines dans la Console Web
  • Système de build : BuildConfig, S2I, déclencheurs ImageStream — entièrement intégrés
  • Registre : Registre interne (ImageStreams) + ICR ; workflows de promotion automatisés
  • Libre-service : Perspective Développeur : déploiement guidé depuis Git ou une image sans Dockerfile

5.2 Posture de Sécurité & Isolation

IKS — Pod Security Standards (PSS) de Kubernetes

IKS applique la sécurité via le modèle Kubernetes standard. L'admission Pod Security (PSA) au niveau des espaces de noms impose les modes privileged, baseline ou restricted. Le profil restricted exige l'exécution non-root, des systèmes de fichiers racine en lecture seule et la suppression des capabilities Linux. Calico NetworkPolicy assure la segmentation L3/L4 (non appliquée par défaut — des politiques explicites sont requises).

ROKS — Security Context Constraints (SCC) — Plus Strict par Défaut

ROKS applique une posture de sécurité plus stricte via le framework des Security Context Constraints d'OpenShift, actif via le contrôleur d'admission SecurityContextConstraint chargé dans la chaîne d'admission du maître. Les SCC contrôlent : plages UID/GID, types de volumes autorisés, accès au réseau/PID/IPC hôte, capabilities Linux, et profils AppArmor/SELinux.

RHCOS applique de plus SELinux en mode enforcing sur tous les nœuds workers — une limite de contrôle d'accès obligatoire supplémentaire absente des workers IKS basés sur Ubuntu.

5.3 Builds & Pipelines CI/CD

IKS — CI/CD Composable
  • Aucun système de build ou CI/CD intégré
  • IBM Cloud Continuous Delivery : Toolchains Tekton gérées ; Code Risk Analyzer ; intégration Secrets Manager
  • ArgoCD / Flux : Opérateurs GitOps pour la réconciliation déclarative des déploiements (déployés via Helm)
  • GitHub Actions / GitLab CI / Jenkins : CI externe via kubectl + Helm + ICR
  • Tekton Pipelines : Déployable en tant qu'opérateur autonome ; pas d'interface Console pré-installée
  • Flexibilité totale : assembler n'importe quelle chaîne d'outils conforme CNCF
ROKS — Plateforme de Build & Pipeline Intégrée
  • OpenShift Builds : Ressources BuildConfig ; pods de build déclenchés par des commits Git, changements d'images ou webhooks
  • Source-to-Image (S2I) : Pousser le code source → obtenir une image OCI exécutable ; aucun Dockerfile requis ; impose des images de base sécurisées
  • OpenShift Pipelines (Tekton) : Opérateur pré-installé ; CRDs Pipeline/Task/PipelineRun ; gestion visuelle dans la Console Web
  • ImageStreams : Redéploiement/rebuild automatique lors des correctifs CVE sur les images upstream
  • IBM Cloud Paks : Nécessitent OCP ; déployés via OperatorHub exclusivement sur ROKS

5.4 Licence, Support & Modèle de Coût

IKS — Consommation Pure de Ressources
  • Coût du nœud worker = infrastructure uniquement (vCPU + RAM + stockage)
  • Aucun frais de licence plateforme intégré
  • Gestion du maître incluse sans frais supplémentaires
  • Classic : réservations 1 an / 3 ans → économies de 30–50 % vs. tarif à la demande
  • Coût d'entrée le plus bas du portefeuille conteneurs IBM Cloud
  • Majorations tarifaires régionales VPC + remises d'utilisation soutenue applicables
ROKS — Calcul + Licence OCP Incluse
  • Coût du nœud worker = infrastructure + frais de licence OCP
  • Nouvelle licence OCP : 1 licence pour 2 vCores (ou 1 cœur physique) ; facturée à l'heure
  • Ancienne licence OCP : 1 licence pour 4 vCores ; facturée mensuellement par worker déployé
  • Licence OCP affichée en sous-poste ou plan séparé sur la facture IBM Cloud
  • BYOL : Droit IBM Cloud Pak ou abonnement Red Hat OCP supprime le surcoût de licence
  • Surcoût effectif vs. IKS : ~25–30 % sur un type de worker équivalent
  • ROKS sur Satellite : frais mensuels fixes + frais worker par vCPU + licence OCP par vCPU

7 Guide de Décision Architecturale

Utilisez le cadre de décision basé sur les scénarios ci-dessous pour orienter le choix de plateforme. Les deux plateformes sont adaptées à la production ; la décision doit être guidée par le contexte organisationnel, les investissements existants dans l'écosystème, les exigences de sécurité des charges de travail et l'analyse du coût total de possession.
Choisir IBM Cloud Kubernetes Service (IKS) quand…
  1. Scénario 1 — Optimisation des Coûts Le budget est la contrainte principale et aucune licence Red Hat existante. Le surcoût de ~25–30 % de la licence OCP n'est pas compensé par les exigences en capacités de la plateforme. Les équipes sont à l'aise avec l'assemblage de leur propre chaîne d'outils (Helm, ArgoCD, Prometheus, registres externes).
  2. Scénario 2 — Conformité K8s Upstream La politique impose les dernières versions mineures Kubernetes upstream. IKS suit la cadence de publication K8s upstream plus fidèlement que ROKS, qui suit le calendrier OCP (généralement en retard de 1–2 versions mineures).
  3. Scénario 3 — Portabilité Multi-Cloud Les charges de travail doivent être portables vers GKE, EKS ou AKS avec un minimum de refactorisation. Les charges IKS utilisant uniquement les APIs K8s upstream sont directement portables ; les charges ROKS utilisant Route, SCC, BuildConfig ou ImageStream nécessitent une adaptation.
  4. Scénario 4 — Modèle d'Opérateurs Composable L'équipe préfère la composition manuelle de l'écosystème d'opérateurs avec des investissements Helm existants pouvant entrer en conflit avec OLM ou nécessiter des grants SCC personnalisés.
  5. Scénario 5 — Cluster Classic Privé Uniquement La conformité impose zéro exposition internet public incluant aucun réseau public sur les workers Classic. IKS le supporte ; ROKS ne le supporte pas.
  6. Scénario 6 — Empreinte Minimale Environnements de périphérie légers, runners CI ou dev/test. IKS supporte 1 worker/zone ; ROKS exige ≥2 workers/zone avec 4 vCPU chacun minimum.
Choisir Red Hat OpenShift on IBM Cloud (ROKS) quand…
  1. Scénario 1 — Écosystème OpenShift Existant L'organisation exploite OCP sur site ou sur d'autres clouds. ROKS offre une cohérence opérationnelle : même CLI oc, mêmes SCC, même OperatorHub, même surface API OCP. Les compétences des ingénieurs et les runbooks sont directement transférables.
  2. Scénario 2 — IBM Cloud Paks Requis Un IBM Cloud Pak fait partie de la solution. Cloud Pak for Data, Integration, AIOps, Business Automation et Security nécessitent OpenShift et se déploient uniquement sur ROKS (ou OCP autogéré).
  3. Scénario 3 — Sécurité & Conformité Entreprise Secteur réglementé (FSI, Santé, Gouvernement) exigeant un OS validé FIPS, SELinux et un durcissement SCC des pods. RHCOS + SCC + OLM fournissent cette posture par défaut, sans configuration supplémentaire.
  4. Scénario 4 — Modernisation des Applications Les équipes de développement ont besoin d'outils guidés pour conteneuriser des applications legacy. S2I, déclencheurs BuildConfig, promotion via ImageStream et la perspective Développeur réduisent considérablement le délai de mise en production.
  5. Scénario 5 — Plateforme Développeur Intégrée Une seule plateforme couvrant orchestration + registre + CI/CD + catalogue + portail + monitoring. ROKS fournit tout cela sans installation de composants supplémentaires.
  6. Scénario 6 — Standardisation Hybride via Satellite Déploiements multi-environnements (IBM Cloud + sur site + périphérie). ROKS sur Satellite offre un plan de contrôle OCP cohérent et des outils unifiés sur tous les environnements depuis un seul plan de gestion IBM Cloud.
  7. Scénario 7 — Optimisation Licence BYOL Abonnement Red Hat OCP existant ou droit IBM Cloud Pak. L'application du droit supprime le surcoût de licence OCP, rendant le coût par nœud comparable à IKS tout en conservant toutes les capacités OpenShift.
